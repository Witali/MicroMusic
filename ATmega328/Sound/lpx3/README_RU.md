# MicroMusic — LPX3-AVR Fast2: проверка динамического словаря 64/128/256/512 Б и Rice v2

Дата: 22.10.2026. Цель: **дополнительное сжатие без изменения PCM** и без переноса поиска паттернов на микроконтроллер. CPU: ATmega328P 16 МГц, 8 кГц аудио. Кодек LPX3 Fast2, 10 коэффициентов LPC, частота аппаратного PWM 62,5 кГц на OC2B/D3.

## Итог на двух сохранённых LPX3-VBR потоках (λ=0.001)

| Новый формат | «Чего тебе нужно?» | «Что ж ты не отвечаешь?» |
|:--|--:|--:|
| L3AV v1, без упаковки поверх VBR | 5809 Б | 4869 Б |
| L3AV v2, динамический словарь 64 Б | 5806 Б | 4859 Б |
| Динамический словарь 128 Б | 5807 Б | 4860 Б |
| Динамический словарь 256 Б | 5808 Б | 4860 Б |
| Динамический словарь 512 Б | 5809 Б | 4861 Б |
| **Rice v2, без словаря** | **5477 Б** | **4644 Б** |

Результаты словаря — лучший объём среди окон на 4/8/16/32/1000 блоков, стратегии с «горячими» 16 записями и фиксированным индексом; если блок дороже исходного, оставляется без словаря. Для Rice выбирается самый короткий из исходной побитной упаковки и Golomb-Rice, параметры `k` рассчитывает ПК на каждом 80-отсчётном блоке. Никакой совместимости v2 со старым v1-декодером нет: нужен прилагаемый C++ код.

Всё сжатие здесь **без потерь относительно уже квантованного L3AV v1**: совпадают все знаковые коды возбуждения, масштабы, параметры LPC и **все PCM8-отсчёты**. Это НЕ обещание сжатия исходного несжатого WAV без потерь. STOI при неизменном эталонном сигнале остаётся тем же самым, что был у соответствующего входного L3AV.

## Почему крупный словарь не выигрывает

Словарь хранит пары `q[2]` в знаковых 8-битных слотах. Слотов: 32 / 64 / 128 / 256. Данные каждого блока могут находиться в режимах 3, 4, 5, 6 бит. Переключение паттернов предварительно рассчитывает кодировщик по окнам; на AVR нет анализа частот, LRU, поиска совпадений и определения жертвы. Словарь хранится в SRAM; команда обновления сразу выдаёт пару в синтезатор и записывает её в выбранный слот.

Старшие уровни индекса не бесплатны: для 512 Б требуется 8-битный номер слота, а в 3- или 4-битном блоке два остаточных значения часто выгоднее записать непосредственно. В первом речевом потоке из 1221 фрагмента по восемь возбуждений не повторился ни один; преимущество дают только короткие пары. Поэтому 256/512 Б в данных примерах неэффективны. Не переносить результат автоматически на музыку/сэмплы с многократным повторением формы волны.

### Кодирование пары (поток битов младшими разрядами вперёд)

Для версии v2 `mode=0x40|b`, где `b` — 2..6 бит на один остаток. Коды: `0 + q0[b] + q1[b]` — буквальная пара; `10 + slot[4]` — ссылка в первые 16 горячих слотов; `110 + slot[indexbits]` — ссылка на остальной словарь; `111 + slot[indexbits] + q0[b] + q1[b]` — заменить выбранный слот и выдать эту пару. В режиме без горячей области используются `0`, `10`, `11` и одинаковые индексы. Слоты записываются как `int8_t[2]`; `q` — signed, декодер не зависит от текущей разрядности исходного блока. Команды никогда не вызывают рекурсию. Номер слота выбирает кодировщик заранее.

### Rice (рекомендуемый вариант для речи)

Контейнер L3AV версии 2, `mode=0x80|(k<<4)|b` с `k` от 1 до `b-1`. Зигзаг: `q>=0 ? 2*q : -2*q-1`, далее нулевые биты унарного частного, единичный терминатор и `k` бит остатка; младшие биты идут первыми. Голосовой синтез, LPC-интерполяция, квантователь и выход Timer PWM **не меняются**. Вычисления оптимального `k` выполняет компьютер. Если Rice не сжимает конкретный блок, он остаётся исходным режимом. При `LPX3_PAIR_DICT_BYTES=0` дополнительная SRAM для словаря не выделяется.

## Ресурсы AVR

Данные измерены для **AVR target relocatable object**, `clang++ -target avr -mmcu=atmega328p -Os -DLPX3_FAST_LPC_INTERP -DLPX3_LPC_SEGMENTS=2`, не полной связанной прошивки. Размер `sizeof(Lpx3AvrCore)` непосредственно из LLVM IR для целевого AVR ABI:

| `LPX3_PAIR_DICT_BYTES` | `sizeof(core)` | Core + очередь 512 Б + малые счётчики (без Serial/стека/ISR) |
|--:|--:|--:|
| 0 | 332 Б | ≈858 Б |
| 64 | 396 Б | ≈922 Б |
| 128 | 460 Б | ≈986 Б |
| 256 | 588 Б | ≈1114 Б |
| 512 | 844 Б | ≈1370 Б |

RAM ATmega328P = 2048 Б. При 512-байтном словаре очередь плюс core уже занимают 1356 Б — Serial, стек и прочие переменные уменьшают запас. Для рекомендованного Rice режима нужен core на 332 Б.

**Реальная производительность ATmega328P в тактах ещё не измерена.** Бюджет на выдачу 8 кГц при 16 МГц — 2000 тактов на отсчёт **в среднем**, включая IRQ, буфер, декодер и обработку пиков LSF. Rice делает меньше чтений битов в этих файлах в сумме (примерно 3,9 против 4,18/4,16), но добавляет ветвление при разборе кода: меньший битрейт сам по себе не доказывает равенство или сокращение тактов. Нельзя говорить о гарантированных «нулевых отставаниях» без прогона на MCU / надёжном циклоточном симуляторе и проверки худшего окна из 20 отсчётов.

В приватных примерах `LPX3_RICE_PROFILE_CHEGO_PRIVATE` и `LPX3_RICE_PROFILE_NEOTV_PRIVATE` находится аппаратная диагностика: Timer0 на 8 кГц, свободный Timer1 на 16 МГц считает реальные циклы `decoder.next()`, Timer2 PWM 62,5 кГц D3, D4 — импульс логического анализатора. Контролировать `underruns`, заполнение 512-байтного буфера, `maxCycles`, накопленные 20 вызовов и следить, чтобы программа помещалась в SRAM / Flash после линковки avr-gcc. Диагностический скетч использует Timer0 и отключает обычную Arduino-функциональность millis()/micros()/delay().

### Контрольный тест

Из корня пакета:

```bash
python3 tests/run_verification.py
# Для приватных речевых данных дополнительно:
python3 tests/run_verification.py --l3av first_original.l3av second_original.l3av
```

Python тест собирает C++-декодер и побайтно сравнивает его output против **оригинального LPC/PCM** при изменённом контейнере. Также проверяет синтетическую запись, в которой 512-байтная таблица действительно получает новые пары и использует как горячие, так и дальние слоты. В приватном пакете результаты составили 9768/9768 и 8232/8232 одинаковых PCM8 с исходным L3AV.

Для ручного кодирования:

```bash
python3 tools/transcode_l3av.py old.l3av new.l3av --strategy rice
python3 tools/transcode_l3av.py old.l3av dyn512.l3av --strategy dictionary --dictionary-bytes 512
python3 tools/transcode_l3av.py old.l3av hybrid.l3av --strategy hybrid --dictionary-bytes 256
python3 tools/make_header.py new.l3av voice_data.h
```

Демонстрационный Arduino скетч: `examples/LPX3_RICE_SYNTHETIC/`. Для синтетической демонстрации 512-байтного динамического словаря, с реально исполненными обновлениями, см. `examples/LPX3_DICT512_SYNTHETIC/`. Реальные записи в публичном source-only ZIP **не входят**. Приватные LPC потоки получены из предоставленных голосовых записей: не публиковать в открытом репозитории без соответствующих прав.

## Дальнейшие работы

1. Физическая линковка/циклосчётчик ATmega328P 16 МГц — обязательный шлюз. Если Rice окажется медленнее настолько, что возникает underrun, использовать v1-данные или уменьшить накладные расходы битового парсера.
2. Перенести распаковку битов в 16-битное окно / fast-table и сравнить такты на реальной плате и exact PCM.
3. Исследовать предсказуемое энтропийное кодирование с небольшой статической таблицей в PROGMEM, а не с крупным динамическим словарём в SRAM; оценивать размер таблиц и такты.
4. Для разных источников отдельно проверить выгоду от словарных паттернов в музыке (огибающие, волновые формы), а не делать вывод по LPC-возбуждению.
