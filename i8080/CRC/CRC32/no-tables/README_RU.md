# CRC-32C для Intel 8080 без таблиц и ОЗУ — дополнительная оптимизация

Дата: 22 октября 2026. Цель: проверка собственной прошивки в ПЗУ 24 или 32 КиБ; процессор Intel 8080, 3,5 МГц, **нет ОЗУ**. Только официальные инструкции 8080. В ПЗУ нет таблиц CRC; таблица из 1024 байт прошлой версии не используется.

## Оптимальные варианты

| Вариант | Машинный код без 4-байтного поля CRC | 24 КиБ, с | 32 КиБ, с | Смысл |
|---|---:|---:|---:|---|
| `u1_halt` | **74 Б** | **6,506** | **8,680** | **Минимальный код** |
| `cachedB` | **81 Б** | **6,374** | **8,489** | Дешёвое ускорение без большого роста размера |
| `u2_halt` | 104 Б | 6,087 | 8,112 | **Рекомендуемый компромисс для ускорения** |
| `u4_halt` | 164 Б | 5,866 | 7,834 | Более быстрое разворачивание |
| `u8_halt` | 284 Б | 5,765 | 7,694 | Самый быстрый из этих *испытанных* вариантов без таблицы |
| `u1_spin` | 77 Б | ~6,50 | ~8,68 | При успехе остаётся в цикле `EI; JMP`, при ошибке `HLT` |

Циклы получены **эмуляцией машинных инструкций** с учётом тактов Intel 8080; времена вычислены как циклы / 3 500 000. На реальной плате возможны отличия из-за частоты, WAIT-состояний и особенностей подключения ПЗУ. Данные измерения не являются аппаратными.

Для сравнения предыдущая реализация `standard_1x` требовала **87 Б** и ~**9,213 с** при 32 КиБ. Новая 74-байтная версия экономит 13 Б (~14,9%) и ускоряет проверку примерно на 5,8%. При использовании небольшого доп. бюджета 81-байтная версия ещё быстрее.

## Где лежат файлы

Файлы имеют имена `crc32c_8080_<24k|32k>_u<1|2|4|8>_<halt|spin>.{asm,bin,hex}`, а для дополнительного компромисса — `crc32c_8080_<24k|32k>_cachedB.{asm,bin,hex}`. ASM является редактируемым исходником, BIN — полный подготовленный образ ПЗУ, HEX — тот же полный образ в формате Intel HEX. После **любого** изменения кода или данных пересчитывайте последние четыре байта.

## Главные изменения по сравнению с 87-байтным кодом

1. **Флаг CY** уже нулевой в начале каждого битового шага. Входное `XRA H` сбрасывает CY; далее либо `JNC` подтверждает CY=0, либо `XRI` в ветке применения полинома сбрасывает его. Поэтому `ORA A` перед `RAR` избыточна.
2. **`MOV A,E` сразу после `JNC` избыточна**: после `MOV A,E; RAR; MOV E,A` аккумулятор A уже содержит сдвинутый младший байт E, так что достаточно `XRI 078H; MOV E,A`.
3. **Конец ПЗУ и 32 битовых шага используют одну пару HL**: перед циклом `LXI H,8020H` для 32 КиБ (`A020H` для 24 КиБ); 32 команды `DCR L` обнуляют L, оставляя H=80h/A0h. `DAD SP; JNC NEXT4` определяет, достиг ли указатель SP границы ПЗУ. Это заменяет более длинную последовательность извлечения SP и сравнения.
4. **Выход** `JNZ FAIL; EI; FAIL: HLT` позволяет использовать одну инструкцию HLT для обоих результатов. До успеха `DI` не даёт включить INTE; в успехе EI устанавливает INTE. Вход INTR должен оставаться неактивным. Если после проверки нужно продолжить выполнение, используйте отдельную схему выхода, а не HLT.
5. `cachedB` хранит B также в A на входе битового шага. Если применяется полином, после `MOV B,A` аккумулятор уже содержит B, и очередная `MOV A,B` не нужна. Ради этого дублируются короткие счётные ветки, что увеличивает код до 81 Б, но ускоряет вычисление.

## CRC-32C точно стандартная

Полином при обработке младшего бита первым: `0x82F63B78`; `init=0xFFFFFFFF`, `xorout=0xFFFFFFFF`. Эталон: `CRC-32C("123456789") = 0xE3069283`. Проверено также на **исполнении самого нового битового ядра машинными инструкциями 8080** (см. `golden_8080.py`). Это НЕ MSB-first вариант из предыдущего архива.

### Подпись ПЗУ

Проверяется **весь** адресный диапазон ПЗУ, включая код и четыре последних байта. В конце помещается сырой (до финальной инверсии) остаток CRC-32C от предыдущих байтов в порядке **little-endian**. С этим полем `raw CRC32C(ROM) = 00000000h`, а обычная финально-инвертированная CRC-32C полного образа равна `FFFFFFFFh`.

Команда для пересчёта уже собранного образа:

```bash
python3 patch_rom.py firmware.bin firmware_patched.bin
```

Для самостоятельной пересборки этих образов:

```bash
python3 generate.py
python3 experiment_cached.py
python3 golden_8080.py
python3 test_all.py         # gcc необходим для быстрой полной эмуляции
```

Примечание: генератор `generate.py` уже включает сборку BIN, HEX и ASM; он заполняет неиспользуемые байты 0xFF. Отдельный скрипт `patch_rom.py` **не вставляет** код CRC в другие прошивки: он только обновляет последние 4 байта уже корректно скомпонованного образа.

## Как тестировали

- Эталон `123456789` в штатном Python и в эмуляции реального набора команд 8080.
- 18 вариантов на 24/32 КиБ: полный проход хорошего образа и пять отдельных повреждений одного бита (в том числе в контрольном поле) с проверкой `INTE` и регистра CRC.
- Ещё 10 полных прошивок со случайно заполненным остальным ПЗУ, пересчётом контрольного поля и исполнением в эмуляторе.
- Эмулятор запрещает запись в ПЗУ/ОЗУ; команда `POP H` только считывает два байта по SP. Никакие `CALL`, `RET`, `PUSH`, `XTHL` не применяются.

Ограничение остаётся принципиальным: **искажённый код самого CRC-проверяющего участка может не запуститься или ошибочно показать успешный результат**. Отсутствие таблицы уменьшает объём исполняемых/контрольных зависимостей, но не делает самопроверку абсолютной. Для более высокой гарантии нужен независимый аппаратный контроль или защищённая начальная программа. Также при использовании `EI/HLT` держите `INTR` неактивным; без RAM обработка прерываний небезопасна.
