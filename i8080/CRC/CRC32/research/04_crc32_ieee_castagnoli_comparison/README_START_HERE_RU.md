# Сравнение Dual CRC-16 и CRC-32 для Intel 8080 — передача агенту

Реальный проект: стартовая проверка **всех 65536 байтов ПЗУ**, CPU **Intel 8080**, плата **без ОЗУ**, без таблиц в ПЗУ, без записи в память. Требуется уменьшать размер проверяющего кода и число тактов на байт, не ухудшая защиту без осознанного компромисса.

## Основной результат

| Проверка (ROM заполнено 0xFF вне кода и footer) | Машинный код | Данные footer | Полный проход (8080 T-states) | Тактов/байт | при 2 МГц |
|---|---:|---:|---:|---:|---:|
| Две CRC-16: `0x0007+0x0009` | **66 Б** | 4 Б | **13 049 432** | **199,119** | **6,525 с** |
| Две CRC-16: `0x0007+0x001B` | 71 Б | 4 Б | 15 015 507 | 229,118 | 7,508 с |
| Стандартная CRC-32/MPEG-2 (IEEE poly `0x04C11DB7`), быстрая | **103 Б** | 4 Б | **58 043 088** | **885,667** | **29,022 с** |
| Стандартная CRC-32/MPEG-2, компактная | **78 Б** | 4 Б | 68 937 832 | 1051,908 | 34,469 с |
| CRC-32C polynomial (`0x1EDC6F41`), MSB-first, быстрая | 103 Б | 4 Б | 58 069 132 | 886,065 | 29,035 с |
| CRC-32C polynomial, MSB-first, компактная | 78 Б | 4 Б | 68 937 832 | 1051,908 | 34,469 с |

Указаны **измерения на эмуляторе команд Intel 8080**, включая инициализацию и `HLT`, без WAIT и с ROM указанного содержания. Дополнительные загрузки/данные могут слегка изменить число тактов из-за условных XOR. Аппаратных испытаний не проводилось. Нельзя считать эти конкретные реализации доказанно оптимальными среди всех возможных программ.

**Ускорение:** Dual `0007+0009` против CRC-32/MPEG-2 (быстрая программа) = **4,448×**.

## Математическая защита (на одном образе 64 КиБ = 524 288 бит)

| Полином, низшие 32 бита | Пропущенные одиночные | Пропущенные двойные | Пропущенные тройные комбинации, точное число | Минимальный span (первый..последний) необнаруженной 4-битной ошибки |
|---|---:|---:|---:|---:|
| Двойная 0007+0009: `0x000E003F` | 0 | 0 | **0** | **2008 бит** |
| Двойная 0007+001B: `0x001C0041` | 0 | 0 | **0** | **2656 бит** |
| IEEE `0x04C11DB7` | 0 | 0 | **5 816 260** | **3007 бит** |
| Castagnoli `0x1EDC6F41` | 0 | 0 | **0** | **5276 бит** |

- Двойные CRC-16 работают как один код с `Q(x)=g1(x)*g2(x)` (над GF(2)), где `g_i(x)=x^16 + p_i(x)`; это **реальный полином степени 32**, а не два отдельных 16-битных поля CRC. Для 0007+0009 он равен `0x1000E003F` целиком.
- Полином 0007, а также полином Castagnoli, делятся на `(x+1)`. Поэтому все **нечётнократные** ошибки обнаруживаются.
- IEEE `0x04C11DB7` не делится на `(x+1)` и имеет конкретную 3-битную коллизию с относительными позициями `[0,41678,91639]` (младшая позиция от конца). Всю 64-КиБ ROM такая тройная ошибка обманывает: эмулятор проверил. Минимальный span тройной коллизии = 91640 бит. Для 0007+0009 и Castagnoli тройных коллизий нет.
- Точные 5 816 260 троек рассчитаны линейным перебором синдромов, с учётом всех переносов на допустимые позиции (не статистическая оценка). Для каждого полинома проверены все 524 288 одиночных синдромов и отсутствие повторов, то есть отсутствие всех пропущенных двойных ошибок.
- Значения минимального span 4-битной ошибки получены полным поиском всех более коротких конфигураций с учётом циклического сдвига; реализации и исходники `search_crc32_4bit_burst.c` / `dual_compare/search_4bit_burst.c`.
- Все варианты обнаруживают любые непрерывные пакеты ошибок длиной до **32 бит**, поскольку степень порождающего полинома равна 32 и свободный коэффициент 1.
- Для случайных **равномерно распределённых** векторов ошибки вероятность пропуска примерно `2^-32`; это не утверждение про вероятности реальных типов аппаратных неисправностей. **Ни одна из схем не защищает от злонамеренной модификации прошивки**: для аутентификации нужна криптография.

**Важная оговорка:** для CRC-32C сравнивается **нерефлектированная** реализация с `init=FFFFFFFF, xorout=00000000` и полиномом `1EDC6F41`. Это НЕ стандартная CRC-32C в формате `refin/refout=true, xorout=FFFFFFFF` и ожидаемым для `123456789` значением `E3069283`. Используются те же порождающий полином и критерии обнаружения ошибок, но другой порядок битов/остатка.

## Intel 8080: быстрый CRC-32 — как он работает

`crc32_mpeg2_8080.asm` реализует **настоящий стандарт CRC-32/MPEG-2**, параметры:

- polynomial `0x04C11DB7`, init `0xFFFFFFFF`, MSB-first, refin/refout=false, xorout=0;
- check(`123456789`) = **`0x0376E6E7`**;
- в адресах `FFFC..FFFF` хранится CRC вычисленное по `0000..FFFB`, в порядке **старший байт первым**;
- проверка всего `0000..FFFF` (включая footer) завершается CRC=0;
- `B:C:D:E` содержат 32-битный CRC; `SP` используется как **ROM-only указатель**, `POP H` читает два байта и увеличивает SP на 2. `XCHG`, `DAD H`, `RAL` выполняют 32-битный сдвиг; если вышел бит31, четыре байта XORятся с байтами полинома. `L` служит восьмибитным счётчиком, `H` удерживает второй прочитанный байт.
- Для проверки завершения `LXI H,0; DAD SP` читает SP без доступа к памяти; при SP=0 после переполнения пройдены 32768 команд `POP H`, то есть **65536 байтов**.
- `DI` перед чтением, `EI;HLT` при успехе; `HLT` без `EI` при ошибке. Вывод INTE может нуждаться в физической проверке.

`POP H` технически использует **указатель стека**. Но выполняет **только чтение**, не делает записи, не вызывает `CALL/RET/PUSH` и не требует RAM. Нужна доступность ROM по адресам 0..FFFF и штатный RESET в `0000h`; прерывания в течение теста должны оставаться запрещёнными.

## Быстрый старт

Все действия только с Python 3 и стандартной библиотекой (кроме `cc` для перебора 4-битных коллизий):

```bash
python3 rom_crc32_8080.py assemble crc32_mpeg2_8080.asm -o test_code.bin
python3 rom_crc32_8080.py demo crc32_mpeg2_8080.asm -o test_rom_64k.bin --poly ieee
python3 rom_crc32_8080.py check test_rom_64k.bin --poly ieee
python3 rom_crc32_8080.py patch YOUR_REAL_ROM.bin -o YOUR_REAL_ROM_CRC.bin --poly ieee
python3 test_crc32_8080.py
```

`rom_crc32_8080.py` поддерживает образы короче 64 КБ (дополняет FF до 65536); последние четыре байта **перезаписывает CRC**. При использовании своего содержимого необходимо вручную разместить проверяющий код с адреса `0000h`. Для 8080 эта проверка не тестирует исправность адресной шины независимо от CRC и не обнаружит ошибку, мешающую выполнению собственного кода.

## Состав файлов

- `crc32_mpeg2_8080.asm`, `.bin`, `_ROM_64KiB.bin`: стандартная CRC-32/MPEG-2, быстрый вариант.
- `crc32_mpeg2_8080_compact.*`: компактная 78-байтная альтернатива.
- `crc32c_msb_8080.*`, `crc32c_msb_8080_compact.*`: полином Castagnoli в MSB-first конфигурации (нестандартный формат CRC-32C).
- `i8080_crc32_tools.py`: компактный ассемблер, независимое вычисление CRC32, эмулятор поддержанного подмножества команд 8080, оценка тактов.
- `rom_crc32_8080.py`: CLI сборки и дополнения контрольными суммами.
- `test_crc32_8080.py`: регрессии (медленны: эмулируют десятки миллионов инструкций).
- `search_crc32_4bit_burst.c`: точный поиск кратчайшей необнаруживаемой ошибки 4 битов.
- `dual_compare/`: исходники, ранее проверенные Dual CRC-16 для честного сравнения.
- `BENCHMARKS.csv`, `VALIDATION_RU.md`: воспроизводимые измерения и результаты.

## Следующая оптимизация

Можно синтезировать байтовый 32-битный алгоритм на регистрах, попробовать другие полиномы/факторизации и тестировать по Pareto-критериям (код/такты/расстояние Хэмминга/минимальный span). **Однако уже существующая пара — 66 байт и 199 тактов/байт — по эффективности существенно превосходит реализованную стандартную CRC-32.** Это измеренное преимущество данных реализаций, а не доказательство отсутствия гораздо более быстрой стандартной CRC32 на 8080.
