# Двойная CRC-16 для Intel 8080 (64 КиБ ПЗУ, без ОЗУ и таблиц)

Исследование идеи: **проверить один и тот же образ ПЗУ последовательно двумя CRC-16 с различными взаимно простыми полиномами, чтобы каждая обнаруживала ошибки, пропускаемые другой**.

## Что реализовано

- Полноценные исполняемые программы Intel 8080, старт с 0000h после аппаратного RESET.
- 2 последовательных обхода всех 65536 байтов ROM командами `LDAX D`.
- Ни одна версия не использует ОЗУ, стек, `CALL`, таблицы CRC.
- Единственный **4-байтный** trailer `FFFC`–`FFFF` обеспечивает нулевой остаток сразу по обоим CRC-16: это не два отдельных CRC-16, а остаток составного CRC-32.
- После двух успешных проверок выполняется `EI; HLT`; при первом несовпадении — `HLT` без `EI`. Семантика и электрическое поведение вывода INTE в реальном железе требуют проверки.
- Набор ассемблерных исходников, *.bin, тестовых образов ПЗУ, скриптов сборки и тестов.

## Сравнение (полный образ 65536 байтов, корректная CRC)

| Пара полиномов | Код, байт | Footer | Полный обход T-states | Тактов/байт | @2 МГц | Минимальный span необнаруженной 4-битной ошибки |
|---|---:|---:|---:|---:|---:|---:|
| `0007 + 0009` | **66** | 4 | 13 049 432 | **199.118530** | **6.525 с** | 2008 бит |
| `0007 + 001B` | 71 | 4 | 15 015 507 | 229.118454 | 7.508 с | **2656 бит** |
| `0007 + 002D` | 72 | 4 | 15 670 867 | 239.118454 | 7.835 с | 1929 бит |

*Полный обход* — с инициализацией, переходами и HLT; все временные оценки выполнены эмулятором Intel 8080 без WAIT. Более короткий минимальный span означает возможность пропустить близко расположенную 4-битную ошибку.

### Как получен результат для четырёх бит

Для любого полинома `Q` степени 32 перебираются все четвёрки
`0 < u < v < w` в порядке увеличения `w`, для которых

```
(1 XOR x^u XOR x^v XOR x^w) mod Q == 0
```

За счёт обратимости умножения на `x` по модулю `Q` (Q(0)=1) любую ошибку из 4 различных битов можно сдвинуть так, что младший ненулевой показатель равен нулю. Поэтому первое найденное `w+1` — **точный минимальный span**, а не случайная оценка. Исходник: `search_4bit_burst.c`.

Найденные образцы недетектируемых четырёхбитовых ошибок (показатели степени от младшего бита):

- `0007 + 0009`: `[0, 777, 1076, 2007]`, span 2008 бит;
- `0007 + 001B`: `[0, 505, 1390, 2655]`, span 2656 бит;
- `0007 + 002D`: `[0, 95, 163, 1928]`, span 1929 бит.

Эти образцы тестируются на целой ROM, включая эмуляцию машинного кода. **Именно четырёхбитовые** ошибки уже могут ускользать от двух CRC-16; расстояние Хэмминга для образа 64 КиБ равно 4.

## Математика

Порождающий полином каждой CRC равен `g_i(x)=x^16+poly_i`. При взаимной простоте `gcd(g1,g2)=1` общая проверка эквивалентна одному CRC с полиномом

```
Q(x) = g1(x) * g2(x)   (умножение GF(2), XOR без переносов)
```

Составные CRC-32 полиномы (нижние 32 бита, старший `x^32` не отображается):

- `0007+0009`: `0x000E003F`;
- `0007+001B`: `0x001C0041`;
- `0007+002D`: `0x002A00C3`.

У полинома `0007` есть множитель `x+1`, поэтому он обнаруживает **все ошибки нечётной кратности** (1,3,5,…).

Периоды синдромов двухбитовых ошибок: `0007` — 32767, `0009` — 57337, `001B` — 59055, `002D` — 65535 бит. Их НОК в каждой выбранной паре превышает 524288 бит, поэтому **все двойные ошибки в 64-КиБ образе обнаруживаются**.

Таким образом, гарантированы любые ошибки с 1, 2 или 3 перевёрнутыми битами. Поскольку степень Q=32, обнаруживаются все пакеты ошибок длиной **не более 32 бит**. Для равномерно случайной ошибки вероятность не обнаружить её составляет около `2^-32`. Это не обещание обнаружить все возможные множественные повреждения.

### Почему нельзя выбирать только самые быстрые полиномы

Например, `0007 + 0003` — тоже пара взаимно простых CRC-16 с защитой от всех 1-, 2- и 3-битовых ошибок для 64 КиБ (НОК двухбитовых периодов выше 524288). Но

```
(x^16 + x^2 + x + 1)(x^16 + x + 1)
   = x^32 + x^18 + x^3 + 1
```

Полученный составной CRC-32 имеет **необнаруживаемую четырёхбитовую ошибку внутри всего 33 бит**! Вот почему нужно исследовать свойства **произведения полиномов**, а не только длину и скорость отдельных CRC.

## Формирование ROM и запуск тестов

Python 3, только стандартная библиотека:

```bash
python3 dual_crc_rom_tool.py dual_crc_0007_0009.asm
python3 dual_crc_rom_tool.py dual_crc_0007_001B.asm
python3 dual_crc_rom_tool.py dual_crc_0007_002D.asm
python3 test_dual_crc16.py
```

Опционально исследовать ближайшую недетектируемую четырёхбитовую ошибку:

```bash
cc -O3 -Wall search_4bit_burst.c -o search_4bit_burst
./search_4bit_burst 0007 0009
./search_4bit_burst 0007 001B
./search_4bit_burst 0007 002D
```

Последовательность действий при формировании образа:

1. Разместить код по адресу 0000h; поместить остальную прошивку до FFFBh включительно.
2. Вычислить 32-битный CRC по байтам 0000h–FFFBh с полиномом `Q`, init=0, MSB-first, xorout=0.
3. Записать четыре байта результата **big-endian** в FFFCh–FFFFh.
4. Убедиться, что CRC-16 обоих полиномов по всем 65536 байтам равны нулю.

Особенность: если записать два независимых CRC-16 по 2 байта, они, вообще говоря, будут влиять друг на друга и условие нулевого остатка по всему ПЗУ не выполнится. Нужен именно **общий 4-байтный хвост** на основании Q.

## Проверки

- Ассемблерный исходник собран повторно; бинарники побайтно совпали.
- Правильный образ ПЗУ и образ со случайной полезной нагрузкой дают положительный результат на эмуляторе.
- Обе CRC независимо равны нулю для каждого правильного образа.
- 131072 чтения ROM (65536 × 2), `DE=0`, верные такты.
- Специальная двойная ошибка, незаметная первой CRC, обнаруживается второй.
- Специальная двойная ошибка, незаметная второй CRC, обнаруживается первой.
- Для 4-битной ошибки, обнаруженной математическим поиском, **оба** CRC возвращают ноль — отрицательная демонстрация ограничения.
- Тесты одиночных, тройных и 32-битных пакетных ошибок на независимой эталонной CRC.

**Ограничения:** физический Intel 8080 не тестировался. CRC по всей ROM сама по себе **не тестирует физическую адресную шину**, не заменяет проверку A15/дешифрации адреса. Если повреждён сам исполняемый проверяющий код, гарантии теста не действуют. При одинаковом систематическом неправильном чтении памяти два прохода также могут оказаться не независимыми отказами.

## Практический выбор

- `0007 + 0009`: рекомендую, если первостепенны небольшой код и скорость: 66 байт, 199 тактов/байт.
- `0007 + 001B`: рекомендую для повышения устойчивости к **локальным 4-битным повреждениям** по критерию наименьшего span: 71 байт, 229 тактов/байт.
- `0007 + 002D`: хорошо изученная пара с примитивной компонентой; однако на рассмотренных метриках размера, скорости и минимального 4-битного span уступает `0007 + 001B`. Не доказано, что последняя лучше при *любых* классах ошибок.

Для дальнейшего поиска: перебор **пар**, вычисление `Q`, расстояния Хэмминга / минимальных 4-битных span при заданной длине образа, затем создание и профилирование Intel 8080 кода для наиболее перспективных кандидатов.
