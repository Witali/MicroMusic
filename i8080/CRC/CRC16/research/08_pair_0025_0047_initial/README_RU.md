# Intel 8080: Dual CRC-16 с полиномами 0x0025 и 0x0047

## Назначение

Готовые тестовые прошивки для 64-КиБ ПЗУ с адресами 0000h..FFFFh и Intel 8080.
Вычисление CRC-16 MSB-first, init=0000h, xorout=0, без reflect, по всем 65536 байтам.
Одна общая контрольная последовательность из четырех байтов по адресам FFFCh..FFFFh;
вычисляется алгоритмом произведения полиномов, как показано ниже. При исправной
памяти обе отдельные CRC-16 завершаются нулевыми остатками.

**Важно:** код в ПЗУ начинается с 0000h. Пример `rom/fast75_demo_64K.bin` содержит
75-байтный код, заполнение FFh, 4-байтный хвост. Hex-образ содержит ВСЕ 64 КиБ,
а не только программу. Для своей прошивки скриптом `tools/build_rom.py` нужно
встроить код или приложение в начало нового образа и затем пересчитать хвост.

Прикладной выбор:
- **`fast75`**: лучший компромисс среди проверенных реализаций — 75 байт, 289.118 T/байт.
- **`compact73`**: минимальный размер с явным DI — 73 байта, 307.001 T/байт.
- `fast_reset74` / `compact_reset72`: минус 1 байт, когда запуск гарантированно
  происходит сразу после **аппаратного RESET**; аппаратный RESET запрещает прерывания.
  Для JMP из уже работающей программы берите вариант с DI.
- `unroll2_120` / `unroll4_210` / `unroll8_390` сокращают накладные расходы на
  ветвления, но увеличивают ROM-код. Самая быстрая из испытанных — 390 байт и
  271.618 T/байт, всего на ~6% быстрее `fast75`.
- `onepass92` делает обе CRC при каждом логическом чтении. Выяснилось, что для
  конкретной пары `0x0025+0x0047` два прохода **одновременно короче и быстрее**.

## Идея оптимизации

Два прохода используют DE как адрес ПЗУ, H как старший байт текущей CRC,
C как младший, B — для сохранения t, HL — для 16-битных сдвигов `DAD H`.
Команда `LDAX D` читает ROM; `INR E / JNZ` обычно даёт 15 тактов на обновление
адреса, раз в 256 байтов обновляется D.

Для CRC-16/0x0025 вычисляется:

    t = data XOR crc_high
    p25(t) = t XOR (t << 2) XOR (t << 5)
           = t XOR ((t XOR (t << 3)) << 2)
    new_crc = (old_crc_low << 8) XOR p25(t)

Для CRC-16/0x0047:

    p47(t) = t XOR (t << 1) XOR (t << 2) XOR (t << 6)
           = t XOR ((t XOR ((t XOR (t << 4)) << 1)) << 1)
    new_crc = (old_crc_low << 8) XOR p47(t)

Сдвиги и XOR внутри HL вычисляются с переносом в 16 бит, а не только с младшим
байтом. Благодаря этому не требуется 8-битный побитный цикл или таблицы.

После первого полного прохода DE=0000h. Если проверка успешна, H=C=00h и эти
нули сразу используются как начальное состояние второй CRC: обнуление регистров
между проходами **не нужно**. Последний `MOV C,A` оставляет младший байт CRC
в аккумуляторе, поэтому `ORA H` заменяет `MOV A,H; ORA C` в быстром варианте.

## Алгоритмические свойства защиты

G1 = x^16+x^5+x^2+1 = 0x10025.
G2 = x^16+x^6+x^2+x+1 = 0x10047.
Взаимно простые: gcd(G1,G2)=1.

Произведение степени 32:
    G = G1*G2 = 0x1006209BB
    POLY32 = G & 0xFFFFFFFF = 0x006209BB.

Установленные свойства для 64 КиБ = 524288 бит:
- обнаруживаются все единичные, двойные и тройные битовые ошибки;
- все ошибки с нечетным числом бит, потому что G1 имеет множитель (x+1);
- все непрерывные пачки ошибок шириной 1..32 бит;
- периоды двухбитовых синдромов 1023 и 21845 бит соответственно,
  LCM=22347435 > 524287 бит => ни одна 2-битовая ошибка не проходит обе CRC;
- минимальный диапазон из четырех бит, который позволяет пропустить
  преднамеренную 4-битовую ошибку: 3921 бит (прежняя пара 0007+0021: 3225).
  Известный четырехбитовый шаблон (степени полинома ошибки): [0, 1065, 1278, 3920].

Это защита от случайной порчи данных, а не криптографическая аутентификация.
Данная пара может пропускать определенные четырехбитовые ошибки (тест это демонстрирует).

## Четырехбайтный CRC-хвост

Последние четыре байта НЕ являются прямой конкатенацией двух отдельных CRC-16.
Они должны быть остатком CRC-32 по произведению G1*G2, рассчитанным по первым
65532 байтам в big-endian порядке. После присоединения хвоста обе CRC-16
по всему полному образу должны равняться нулю.

Пример построения:

```sh
python3 tools/build_rom.py bin/fast75.bin my_rom_64K.bin --hex my_rom_64K.hex
```

`rom/fast75_demo_64K.bin` и `hex/fast75_demo_64K.hex` готовы для тестового ПЗУ,
заполненного FFh вне программы, с корректным CRC в конце.

## Интерфейс результата

После завершения проверки:
- УСПЕХ: инструкция `EI`, затем `HLT`.
- НЕСОВПАДЕНИЕ: переход прямо на `HLT`, при отключенном INTE.

На плате с подключенным индикатором к INTE это может использоваться как сигнал
успешности теста. Код НЕ формирует звуковых сигналов, а `HLT` намеренно
останавливает CPU. При подаче внешних прерываний после `EI` процессор может
выйти из HLT. Реальную работу вывода INTE требуется проверить аппаратно.

Если запускаете CRC из вызывающей прошивки, нужны изменения на возврат и
отображение ошибки — текущая версия ожидает запуск с 0000h и завершает HALT.

## Проверки

С помощью независимой C-модели машинных инструкций проведены тесты целостного
чтения памяти для всех восьми вариантов; проверено фактическое число тактов,
сравнение двух CRC с независимым побитным калькулятором, битовые повреждения
внутри ROM, в хвосте, на границе A15, случайные данные и специально
подобранная необнаруживаемая четырехбитовая комбинация. Всего 992 полных
исполнения на программном процессоре (124 на вариант).

Повреждения именно кода проверки не обязаны корректно диагностироваться:
процессор может выполнить некорректную команду раньше, чем завершит CRC.
CRC также НЕ является тестом физической работы всех адресных линий,
а `DI` и `EI` изменяют внешний сигнал INTE в зависимости от схемы платы.

## Состав архива

- asm/ — комментированные 8080-ассемблерные исходники всех профилей;

- hex/ — те же образы в Intel HEX;
- tools/build_rom.py — формирование четверки CRC в конце ROM;

- BENCHMARKS.csv, TEST_RESULTS.txt, SHA256SUMS.txt.
