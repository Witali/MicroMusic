# Поиск полиномов CRC-16 для Intel 8080, 22.10.2026

## Задача

Проверка всего ПЗУ 65536 байтов процессором Intel 8080, начиная с RESET.
Без ОЗУ, стека, подпрограмм и таблиц. Последние два байта ПЗУ — старший и
младший байты CRC-16; начальный CRC=0, поток MSB-first, xorout=0. Проверяется
весь образ, включая footer; исправный образ даёт остаток 0. Такты 8080 считаются
без WAIT.

В этой папке есть **новый проверенный вариант 0x0007 (36 байт)** и три
ранее разработанных варианта, повторно проверенных в этом исследовании.

## Ключевой результат

| poly (обычная усечённая запись) | код | тактов/байт | тактов на 64 KiB | 2MHz | период | ошибки нечётной кратности |
|---|---:|---:|---:|---:|---:|---|
| `0x0009` | 33 | 94.059 | 6164278 | 3.082 сек | 57337 | нет гарантии |
| **`0x0007`** | **36** | **105.059** | **6885169** | **3.443 сек** | **32767** | **все обнаруживаются** |
| `0x001B` | 38 | 124.059 | 8130353 | 4.065 сек | 59055 | нет гарантии |
| `0x002D` | 39 | 134.059 | 8785713 | 4.393 сек | 65535 | нет гарантии |

Код + два CRC-байта в конце ПЗУ: соответственно 35, 38, 40, 41 байт.
Данные по программам повторно получены эмуляцией **каждого шага** инструкций Intel 8080.
Тест 0x0007 проходит все 65536 адресов ровно по одному разу.

## Полный перебор

`tools/scan_all_polynomials.c` перебирает все 32768 полиномов
`x^16 + poly(x)` с единичным свободным членом (poly от 0x0001 до 0xFFFF,
нечётный). Измеряет период последовательности ненулевых синдромов `x^i mod G(x)`.
Результаты: `data/all_32768_polynomials.csv`.

* Примитивных полиномов с периодом 65535: 2048.
* Полиномов с множителем (x+1) и максимальным периодом 32767: 1800.
* Минимальная степень poly(x) для примитивного 16-битного CRC: 5;
  пример `0x002D` = 1+x^2+x^3+x^5.
* Минимальная степень poly(x) для CRC с множителем (x+1) и периодом 32767: **2**;
  `0x0007` = 1+x+x^2.

Степень *усечённого poly(x)* не означает разрядность CRC: все варианты содержат
старший член x^16, то есть это именно CRC-16.

## Математические гарантии и ограничения

* Все кандидаты с единичным свободным членом обнаруживают любые одиночные
  ошибки и любые пакеты ошибок, охватывающие не более 16 последовательных бит.
* Полином с множителем x+1 обнаруживает любые ошибки с нечётным числом
  изменённых битов — 1, 3, 5, ... независимо от длины сообщения.
* Количество незамеченных двойных ошибок в N-битном кодовом слове при
  периоде T рассчитывается точно как:

  `sum(N - k*T for k in [1,2,...] while k*T<N)`.

* Для CRC на непрерывном 64-KiB образе N=524288 бит; максимальный
  теоретический период 16-битного CRC равен 65535, поэтому обнаружить
  **все** двойные ошибки невозможно ни одним CRC-16 с таким форматом.
* При разбивке на блоки **2048 байт включая 2 байта CRC** `0x0007` не пропускает
  ни одной одно-, двух- или трёхбитовой ошибки **внутри любого одного блока**,
  то есть имеет HD>=4 для такого размера блока. Это математический анализ:
  реализация контрольных сумм по 32 блокам потребует отдельного кода
  проверки границ и 64 байта под CRC, который в архив НЕ включён.

### Точный счёт для 64KiB

| poly | невыявленные пары бит | доля всех двойных ошибок | тройные ошибки |
|---|---:|---:|---|
| 0x002D | 1,835,044 | 1.33517e-5 | 366,503,875,808 |
| 0x001B | 2,068,324 | 1.50491e-5 | 364,472,678,733 |
| 0x0009 | 2,138,427 | 1.55591e-5 | 359,024,367,301 |
| 0x0007 | 3,932,296 | 2.86113e-5 | 0 |

Всего возможных пар ошибок `C(524288,2)=137438691328`.
Тройные ошибки подсчитаны точно при помощи XOR-преобразования Уолша—Адамара
по частотам каждого 16-битного синдрома, а не моделированием случайной выборки.
Примечание: вероятность здесь условна **при равномерном выборе комбинаций
указанной кратности**, это не оценка риска конкретной микросхемы ПЗУ.

### Уязвимость к близко расположенным ошибкам

| poly | кратчайшая пропускаемая тройка (охват, бит) | кратчайшая пропускаемая четвёрка (охват, бит) |
|---|---:|---:|
| 0x0009 | 17 | 20 |
| 0x0007 | никогда | **17** |
| 0x001B | 236 | 64 |
| 0x002D | 568 | 57 |

В частности, для 0x0007 шаблон ошибок `x^16+x^2+x+1` (четыре бита
в области длиной 17 бит) **не обнаружится**, что является важным компромиссом.
Для 0x0009 шаблон `x^16+x^3+1` (три бита в 17-битной области) тоже не
обнаружится — одна из причин НЕ рекомендовать его для ответственного тестера.

## Файлы

- `src/poly0007_36B.asm/.bin` — новый вариант, полином 0x0007.
- `src/poly002D_39B.asm/.bin` — старая примитивная CRC-16, оптимальная по периоду.
- `src/poly001B_38B.asm/.bin` — промежуточный компромисс.
- `src/poly0009_33B.asm/.bin` — рекорд по скорости, но слабый локальный тройной шаблон.
- `tools/rom_tool.py` — сборка/проверка/патч ПЗУ с выбором полинома.
- `src/poly0007_demo_64KiB.bin` — готовый исправный демонстрационный образ.
- `tools/crc8080_tools.py` — ассемблер ограниченного набора инструкций 8080,
  эмулятор с подсчётом T-state, генератор/проверка CRC.
- `tests/test_polybench.py` — тесты всех четырёх вариантов, проверка точных тактов,
  повреждений, случайных ROM, известных коллизий.
- `tests/RESULTS.txt` — фактический повторный вывод тестов.
- `tools/scan_all_polynomials.c` — полное сканирование нечётных 16-битных полиномов.
- `tools/crc16_syndrome_math.py` — точные счётчики двух- и трёхбитовых ошибок;
  **требуется NumPy** (прочие тесты обходятся стандартной библиотекой Python).
- `tools/error_burst_weights.py` — поиск минимального размаха незамеченных
  троек и четвёрок ошибок по локальным синдромам.
- `tools/four_bit_bursts.c` — число необнаруженных четвёрок в ограниченном окне.
- `data/*.csv` — исходные данные полного сканирования и сравнений.

## Запуск

```sh
python3 tests/test_polybench.py
python3 tools/rom_tool.py build odd-fast demo.bin
python3 tools/rom_tool.py check odd-fast demo.bin
python3 -m pip install numpy
python3 tools/crc16_syndrome_math.py --bytes 65536
cc -O3 tools/scan_all_polynomials.c -o /tmp/scan_all_polynomials
/tmp/scan_all_polynomials > /tmp/all.csv
```

Чтобы собрать прошивку 0x0007 как CRC-проверяемый 64-KiB образ:

```python
from pathlib import Path
from tools.crc8080_tools import assemble,patch_rom
code,_ = assemble(Path('src/poly0007_36B.asm').read_text())
Path('poly0007_rom_64KiB.bin').write_bytes(patch_rom(code,poly=0x0007))
```

## Рекомендации

* Одна CRC на весь ПЗУ 64KiB, приоритет обнаружения двойных ошибок:
  **0x002D / 39B / 134T/byte**. Можно использовать 0x001B, если выигрыш ~10T/byte
  важнее прибавки ~13% к числу пропускаемых пар.
* Быстрый тестер, приоритет гарантированного обнаружения всех нечётных ошибок:
  **0x0007 / 36B / 105T/byte**, но учитывать пропуск некоторых четверных ошибок
  на расстоянии 17 бит.
* Для существенного усиления обнаружения повреждений важнее не менять полином,
  а проверять **отдельные блоки** 1—2KiB с собственными CRC и хранить
  эталоны в ПЗУ. Это изменит формат образа и код проверки.
* Нельзя считать самостоятельную проверку прошивки абсолютной: повреждение
  самой проверяющей программы тоже может нарушить диагностику.
* CRC не криптографическая защита: намеренную подмену данных с пересчётом
  проверочной суммы она не обнаружит.

## Источники для теории CRC

- Koopman CRC selection: https://users.ece.cmu.edu/~koopman/crc/
- Koopman HD=3: https://users.ece.cmu.edu/~koopman/crc/hd3.html
- Koopman HD=4: https://users.ece.cmu.edu/~koopman/crc/hd4.html
- Важно: у Koopman колонка с сокращённым полиномом иногда записана в формате
  «полный полином >> 1», а здесь приведена обычная нижняя 16-битная часть
  `G(x)` без старшего x^16. Для прямого сравнения пользуйтесь полной формой.

## Достоверность

Размеры и такты проверены на программной модели выбранного набора команд Intel
8080, независимая побитная CRC реализована отдельно от машинной программы.
Математика синдромов проверена кодом. Проверка реальным Intel 8080,
с физическими микросхемами EPROM/Flash, НЕ проводилась.
