# MicroMusic LPX4 — ускоренный ПК-кодировщик, 23.10.2026

## Главное

Ускорен **офлайновый кодировщик** LPX4/L4HY v2 для ATmega328P. Поток, качество звука, C++/AVR-декодер, его Flash/RAM и нагрузка при воспроизведении **не меняются**. Проверено побайтное совпадение ускоренной и эталонной реализации.

* `tools/fast_lpx4.py` — Numba-компиляция оценки периодов, коэффициента усиления и вариантов Rice. Соответствие режимов и правил выбора `tools/lpx4.py:select_chunk`.
* `encoder_vbr/tools/fast_vbr.py` — подготовка LPC/LSF-контекста один раз, векторизация вычисления необходимого возбуждения, один скомпилированный перебор квантователей; итоговый выбранный вариант **создаётся старой эталонной функцией**, чтобы сохранить точные байты.
* `tools/auto_search_lambda.py` — по умолчанию `--encoder-backend fast`, опция `--encoder-backend reference` возвращает старый кодировщик.
* `tools/benchmark_fast_encoder.py` — воспроизводимый бенчмарк без приватных аудиозаписей.
* `tests/test_fast_encoder.py` — сравнительные тесты VBR и LPX4, включая случайные истории возбуждения.

Первый запуск Numba тратит время на JIT-компиляцию. Для короткого единственного файла общее ускорение может быть меньше. Сравнение относится к ПК на конкретной машине; это НЕ измерение тактов AVR.

## Эквивалентность результатов

* Полные 48-λ прогоны дали ровно те же утверждённые файлы: 4 931 Б и 4 052 Б. SHA-256 **бит в бит** совпали со старыми релизами. Показатели STOI/SNR неизменны.
* Для 12-λ и 8-λ контрольных прогонов совпали метрики и хеши PCM **каждого** кандидата.
* В тесте синтетических данных семь значений `lambda` дали те же файлы L3AV, `exact.pcm8`, `q_signed.i16`; 360 случайных комбинаций режима/истории сопоставлены с прежней функцией.
* Пройдены структурные тесты исходного LPX4-декодера (включая повреждённые потоки).

## Установка и запуск

```bash
python3 -m pip install -r requirements.txt
# Собрать host-декодер из неизменённых исходников:
g++ -O3 -std=c++11 -Isrc src/Lpx4HybridCore.cpp tests/decode_host.cpp -o decoder

# Самопроверка и демонстрационный бенчмарк:
python3 -m unittest discover -s tests -p 'test_fast_encoder.py' -v
python3 -m unittest discover -s tests -p 'test_autotuner.py' -v
python3 tools/benchmark_fast_encoder.py --repeats 5
```

Пример поиска на сохранённых исходных LPC/LSF-данных (из приватного тестового комплекта):

```bash
python3 tools/auto_search_lambda.py \
  --source source_v1.l3av --wav reference.wav \
  --lsf-json source_lsf_co.json --coeff-trace source_coeff_trace.csv \
  --legacy-lpx3 source_legacy.lpx3 \
  --decoder ./decoder --baseline before.l4hy \
  --output after_fast.l4hy --report after_fast.json \
  --encoder-backend fast
```

Для сравнения без оптимизации замените `fast` на `reference`. Наличие подготовленного `source_lsf_co.json` и `source_coeff_trace.csv` по-прежнему необходимо: универсальный WAV→LSF frontend не реализован в этом пакете.

## Важные ограничения

* **Декодер ATmega328P не менялся**. Требование непрерывной выдачи 8 кГц на CPU 16 МГц остаётся неподтверждённым аппаратным измерением — ускорение ПК-энкодера его не доказывает и не ухудшает.
* `fast=True` для LPX4 применяется к **точному** кодированию возбуждения; отдельные экспериментальные режимы с потерями остаются в эталонной реализации, если вызваны с конечным `min_snr`.
* `Prepared` должен использоваться только для тех же исходных PCM и LPC/LSF-данных: проверка PCM контекста предотвращает случайное переиспользование на другой волне той же длины.
* STOI на тех же записях, что использовались при подборе параметров, не является оценкой обобщения на другие голоса. Публичный ZIP не содержит приватных записей.
