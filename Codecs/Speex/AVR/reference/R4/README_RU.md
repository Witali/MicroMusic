# Speex NB8 для AVR — R4, оптимизация LSP/LPC

**Дата:** 23 октября 2026 г.  **Цель:** ATmega328P, 16 МГц, 2 КБ SRAM, 32 КБ Flash, Speex NB mode 3, 8 кГц, 8 кбит/с (20-байтовые кадры, 160 отсчётов).

## Итог: выбран Cache10-Fused (100% совпадение PCM)

Код по умолчанию: `src/speex_nb8.c`. Он использует оптимизации FastLPC R3 и **один дополнительный точный быстрый путь**:

1. Декодируются 10 LSP-значений из кодовых книг.
2. В **том же цикле** вычисляется побитовое XOR-отличие от `old_lsp[10]`.
3. Если после первого кадра все значения равны предыдущим, 4 промежуточные LSP→LPC-конверсии не производятся, `previous_lpc[10]` сохраняется.
4. Алгоритм восстановления возбуждения и покадрового синтеза PCM не изменён; поток Speex остаётся стандартным.

Обоснование: в конце предшествующего кадра `previous_lpc` равен коэффициентам последнего подкадра, построенным для `old_lsp`. Если `new_lsp==old_lsp`, четыре интерполированных вектора LSP после применения margin также одинаковы. Поэтому 4 повторные конверсии вычислили бы те же коэффициенты. **Звук не изменяется.**

## Реально проверено

- Сравнение хостовым GCC с FastLPC R3 на **11 потоках / 1058 кадрах / 169280 PCM-отсчётах**. Результат идентичен побайтно, включая синтетическую русскую речь, 16-кГц Speex WB lowband, белый шум, импульсы и повреждённые mode-3 последовательности.
- Сборка AVR LLVM Clang 17 (`-O3`) в ELF-объект + листинг.
- Интерпретация исполняемых AVR-инструкций LLVM: 3 начальных кадра каждого из сигналов `speech_ru`, `silence`, `random_40` для базовой и новой реализации. PCM интерпретатора совпадает с хостовым.
- AddressSanitizer/UBSan: **12 000 случайных mode-3 кадров**, проверка отказа для всех остальных заголовков.
- `src/avr_player.c`, `src/avr_player_16k.c`: LLVM объектная компиляция, однако полного GCC-линкования и аппаратного прогона нет.

### Циклы: фактические короткие прогоны AVR-интерпретатора

| Сценарий | FastLPC R3 | R4 Cache10-Fused | Статус |
|:--|--:|--:|:--|
| Speech RU, первые 3 кадра (изменение LSP) | 205570 | **204062** | PCM совпал |
| Silence, первый кадр | 204420 | **202668** | PCM совпал |
| Silence, повтор LSP (2-й и 3-й кадры) | ~204183 | **164374–164375** | PCM совпал |
| Random, первые 3 кадра | 205985 | **204617** | PCM совпал |

Цифры относятся к **LLVM AVR** и интерпретатору инструкций с моделью libc/libgcc, а не к avr-gcc и реальному ATmega328P. 320000 тактов на кадр (20 мс, 16 МГц) — полный бюджет, из которого нужно вычесть время ISR и ввода/вывода.

В синтетическом `speech_ru` 46 из 147 кадров имеют те же LSP-индексы, что и предыдущий кадр (31,5%). Если экстраполировать расходы коротких прогонов на всю эту последовательность, получаем ориентировочно **205161 → 191643 такта на кадр (минус 6,6%)**. **Это прогноз, не полный 147-кадровый AVR-замер.** Доля повторов на живых голосах ещё не измерена.

### Память и размер

- Объект декодера LLVM `-O3`: `.text = 11184 байта` (против 9974 у предыдущего R3, +1210 байт), `.progmem.data = 132 байта`.
- Объект плеера на 8 кГц: `.bss = 1261 байт`, на 16 кГц: `.bss = 1262 байта`, `.data = 1 байт`.
- Максимальная глубина стека в модели из коротких прогонов для новой версии: **235 байт**. Сохранённая AVR RAM структура состояния не увеличена.
- Flash / RAM после AVR GCC линковки **не проверены**; приведённое выше — по LLVM объектным секциям, не суммарный размер HEX.

## Почему не убрали LSP→LPC полностью?

Спектральная оболочка в Speex задаётся двумя полиномами LSP:

`A(z) = [(1 + z^-1) P(z) + (1 - z^-1) Q(z)] / 2`

где P и Q — произведения пяти квадратичных звеньев. Стандартный синтезирующий фильтр — `H(z)=1/A(z)`. Поэтому нельзя просто поставить звенья P и Q в последовательный 10-звенный IIR-конвейер: знаменатель содержит **сумму**, а не произведение. Полноценная прямая LSP/lattice-реализация математически возможна, но требует другой структуры и не гарантирует меньшего числа операций на PCM-отсчёт. **Она не была реализована или измерена в этом исследовании**.

Если математически эквивалентный прямой LSP-фильтр реализован с достаточной точностью, он должен выдавать почти тот же звук. Иногда иная численная схема даёт меньше шума округления, но само исключение преобразования не восстанавливает потерянную при кодировании информацию. Предыдущие эксперименты с двумя/одним преобразованием меняли коэффициенты между подкадрами: это не «нативный» эквивалент LSP-фильтра и поэтому даёт ошибку.

## Как воспроизвести

Для Linux с GCC, Python3, FFmpeg (опционально), LLVM Clang (для AVR модели):

```bash
cd src
make host
cd ..
python3 tests/verify_host.py
python3 tests/benchmark_llvm_avr.py --frames 3
```

Проверка санитайзерами (на ПК):

```bash
gcc -O1 -g -fwrapv -fno-omit-frame-pointer -fsanitize=address,undefined -Isrc \
  src/speex_nb8.c src/speex_tables.c src/cos_table.c tests/fuzz_harness.c -o fuzz
ASAN_OPTIONS=detect_leaks=1 UBSAN_OPTIONS=halt_on_error=1 ./fuzz
```

При наличии AVR GCC + avr-libc:

```bash
cd src
make avr       # firmware.hex, PWM 8 кГц
make avr16k    # firmware16.hex, 16-кГц PWM-интерполяция NB8 lowband
```

Реальное воспроизведение требует подтвердить сроки выполнения ISR + декодера, затраты на чтение Flash и отсутствие underrun на плате. В этой среде avr-gcc нет, и полноценно собранного/проверенного HEX нет.

В качестве более реалистичных тестов — `tests/download_real_speech.py` и `REAL_SPEECH_SOURCES.md` (русский/английский, мужской/женский живые голоса). Файлы не вложены в архив, требуется скачать их по CC-условиям.
