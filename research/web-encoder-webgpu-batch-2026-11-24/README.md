# LPX WebGPU: сохранённый эксперимент

Экспериментальная реализация сохранена в ветке **`codex/lpx-webgpu-batch`**,
коммит **`25b401cd3aac78002ea81797788dd48abe653931`**. Исходный вариант с одним
блоком на обмен также сохранён в `codex/lpx-webgpu`, коммит `a0939f12`.
В `main` перенесены описание и исторические протоколы измерений. Рабочий WebUI
в `main` продолжает использовать WASM SIMD с обычным WASM fallback.

Решение: оставить WebGPU исследовательской веткой. Пакетирование значительно
ускорило сам GPU-путь, но разница с уже оптимизированным SIMD невелика, зависит
от режима и сопоставима с разбросом части длинных замеров. Добавляются запуск
GPU, память, требования к браузеру и отдельный асинхронный транспорт.

## Что реализовали

1. Перенесли точный перебор кандидатов возбуждения LPX в вычислительный
   WGSL-шейдер: 32 кандидата P4 или 320 P6 на группу из 20 отсчётов. Анализ,
   адаптивный выбор, упаковка и окончательная проверка декодером остались в
   общем C++-кодировщике. WebAssembly JSPI приостанавливает WASM на время GPU.
2. Сохранили целочисленный синтез, порядок кандидатов и выбор первого при равных
   ошибках. Сумма квадратов хранится в двух `u32`, без приближения через `f32`.
   Каждый возвращённый победитель повторяется на CPU с проверкой полной истории
   LPC, кольца возбуждения, деэмфазиса и точной ошибки.
3. Первый вариант обменивался данными с CPU после каждого блока из 160
   отсчётов. Он оказался заметно медленнее SIMD.
4. В отдельном коммите `ba1ba5ae` вынесли общую подготовку периода, усиления
   и масштаба: эти параметры зависят от исходника и могут готовиться заранее.
5. Объединили до 128 последовательных блоков в одно задание. GPU передаёт
   состояние победителя следующему блоку через копирование буфера; один обмен
   возвращает результаты всего пакета. Передаются только начальное состояние
   и используемые параметры. Независимого кодирования блоков и сброса истории нет.
6. Кэш проверяет фактическое входное состояние и параметры перед выдачей каждого
   результата. Потенциальный специальный переход на тишину ограничивает пакет.
   Размер 1 остаётся доступным для контрольного сравнения. В ветке есть явный
   режим WebGPU и переход на WASM при недоступности API, устройства или JSPI.

Подробности и небольшой переиспользуемый пример точного сложения ошибки — в
[WebGPU cookbook](../../docs/webgpu-asm-cookbook/README.md).

## Проверка точного совпадения LPX

- 29 сценариев сравнивают полный LPX с CPU и SIMD: уровни точности и частоты,
  тишина, клиппинг, шум, хвосты пакетов, полный адаптивный P8, нормализация,
  непрерывный V9 Long, настоящий Worker и путь WAV → OPFS → потоковый Worker.
- Независимый CPU-перебор проверяет победителя, импульсы, широкую сумму ошибок
  и полное состояние. Отдельные цепочки из 2, 7 и 128 блоков проверяют передачу
  состояния внутри GPU; пакеты 1, 2, 7 и 128 дают одинаковые LPX-байты.
- В протоколе сохранены 12 сравнений с новой нативной CPU-сборкой.
  Ещё [12 проверок обычного seed-пути](seed-parity.json) включают паузы и явно
  выбранную C-арифметику внутри того же GPU-модуля. Все файлы совпали побайтно.
- Все измеренные длинные результаты сравниваются с CPU по полному файлу;
  независимый декодер проверяет длину. Общая регрессия ветки: **201 passed,
  34 skipped, 0 failed** из 235 проверок. Пропущенные необязательные проверки
  не считаются выполненными.
- [Отключение GPU](fallback.json) проверено отдельно: выбирается WASM SIMD,
  в том числе через Worker и временное хранилище исходника.

## Сравнение полного времени кодирования

Windows x64, HeadlessChrome 158, NVIDIA Blackwell; Emscripten 6.0.12 / Clang 24,
`-O3 -ffp-contract=off -msimd128`. Детерминированные синтетические сигналы,
один полный прогрев и три прогона с чередованием порядка. Измеряется весь вызов
кодирования; в потоковом режиме включены сборка и проверки полного результата.
Загрузка модулей и запуск устройства учтены отдельно. Компиляция и другие
тестовые процессы параллельно финальному замеру не запускались.

| Вход / режим | WASM SIMD, медиана | WebGPU пакетами, медиана | WebGPU по одному блоку |
| --- | ---: | ---: | ---: |
| P4 / 8 кГц / 2560 отсчётов / быстрый | 14,5 мс | 17,3 мс | 66,1 мс |
| P6 / 16 кГц / 2560 отсчётов / быстрый | 15,4 мс | 14,5 мс | 62,5 мс |
| P8 / 8 кГц / 640 отсчётов / полный | 251,3 мс | 263,0 мс | 310,0 мс |
| P4 / 8 кГц / 60 с + 1 отсчёт / потоковый | 4,058 с | 3,977 с | Не измерялось |
| P6 / 16 кГц / 60 с + 1 отсчёт / потоковый | 6,405 с | 5,561 с | Не измерялось |
| P6 / 8 кГц / 300 с + 1 отсчёт / потоковый | 21,094 с | 20,006 с | Не измерялось |
| P6 / 8 кГц / 30 с + 1 отсчёт / весь вход | 1,080 с | 0,937 с | Не измерялось |

На пятиминутном входе три измеренных GPU-прогона обработали 45006 блоков за
354 обмена: примерно **127 блоков вместо одного на обмен**. На коротких быстрых
P4/P6 пакетирование ускорило GPU-путь в **3,82 / 4,31 раза**, но не дало такого
же преимущества перед SIMD. P4 на коротком входе и полный P8 остались медленнее.
Длинные GPU-прогоны немного быстрее по медианам; исходные значения показывают
заметный разброс. Это не доказательство универсального выигрыша на реальной
речи, музыке, другом браузере или другом GPU.

Запуск GPU занял 393,1 мс против 10,3 мс для SIMD; запуск и первое короткое
кодирование — 408,6 против 21,3 мс. Кэши драйвера не очищались. Пакеты добавляют
до 1396224 Б WASM-памяти для заданий и результатов и 1861320 Б GPU-буферов,
без учёта драйвера, pipeline и памяти рабочих групп. GPU-модуль: 450768 Б,
сопоставимый SIMD-модуль: 446996 Б. Оценки не относятся к Flash, SRAM или
поддержке реального времени микроконтроллерами.

## Где находятся код и воспроизводимые данные

[benchmark.json](benchmark.json), [fallback.json](fallback.json) и
[seed-parity.json](seed-parity.json) перенесены из `25b401cd` без изменения.
Это исторические протоколы экспериментальной ветки: их `assetsSha256` относится
к файлам той ветки, а не к текущим исходникам `main`. Медианы выше округлены;
сырые времена и хеши сохранены в JSON. Частные записи и временные медиа в
документацию не включались.

В коммите `25b401cd` сохранены:

- `web-player/lpx/webgpu-search.wgsl` — точный перебор;
- `web-player/lpx/webgpu-search.js` — буферы и пакетная отправка;
- `web-player/lpx/native/webgpu-search.cpp` — адаптер общего C++-поиска;
- `web-player/lpx/encoder-webgpu.js` — JSPI и выбор режима;
- `web-player/scripts/build-lpx-webgpu.mjs` — сборка;
- `web-player/scripts/benchmark-lpx-webgpu.mjs` — сравнение, включая `--long`;
- `web-player/tests/helpers/lpx-webgpu-seed.mjs` — паузы и C fallback;
- `research/web-encoder-webgpu-batch-2026-11-24/README.md` — полные команды и приёмка.

Например, описание из сохранённой ветки можно прочитать без переключения `main`:

```powershell
git show 25b401cd3aac78002ea81797788dd48abe653931:research/web-encoder-webgpu-batch-2026-11-24/README.md
```

Для повторения нужны существующий Emscripten SDK, Chrome/Playwright, аппаратный
WebGPU и JSPI. Требуется отдельная рабочая копия сохранённой ветки. Перед новым
решением о включении WebGPU полезны измерения на независимой речи/музыке и
разных устройствах; результаты этого эксперимента такого решения не заменяют.
