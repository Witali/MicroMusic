MICROMUSIC / ATtiny13A WEB PLAYER

ЗАПУСК
Из корня репозитория:
  node web-player/scripts/serve.mjs
Откройте http://127.0.0.1:8133/web-player/
Другой порт: node web-player/scripts/serve.mjs 8134

Установка npm-пакетов и сборка не нужны. По умолчанию работает WASM-движок;
для WASM готовый wasm/avr.wasm включён в репозиторий. Требуется браузер с Worker,
Web Audio и AudioWorklet. Звук включается кнопкой «Слушать».
Страницу следует открывать через localhost или HTTPS, не через file://.
Сервер доступен только с этого компьютера; Ctrl+C завершает его работу.

ВОЗМОЖНОСТИ
Пять прошивок: Люмьер, Алисия, Турецкий марш, Children, Greensleeves.
Точный состав, музыкальные ограничения, размеры и длительности: ../README.txt.
Выбор, поиск, пауза/сброс, громкость, RC-фильтр4/6/9/12 кГц (по умолчанию9),
Space вне элементов управления. Осциллограмма, средний PWM, длительность ISR,
потери IRQ, регистры, PC, такты и Flash. Flash/EEPROM HEX скачиваются прямыми
ссылками с атрибутом download. На узком экране у вывода 6 остаётся динамик,
а длинная линия, RC и подпись PB1 скрываются. При скрытии вкладки музыка
продолжает играть в фоне. Кнопка «Пауза» и Space останавливают воспроизведение.
Контроль темпа учитывает реальные запросы AudioWorklet и отдельно показывает
накопленное отставание. Это не измерение задержки звукового устройства.
Под транспортом находится переключатель «Движок эмуляции»: JS / WASM.
При открытии страницы выбран WASM. JS можно выбрать вручную;
загружается только выбранный движок.
Смена движка сбрасывает прошивку на начало и ставит плеер на паузу,
сохраняя выбранную прошивку, громкость и RC-фильтр. Выбор движка сохраняется
при смене прошивки и сбросе, но не после перезагрузки страницы.

ФЬЮЗЫ В ГЛАВНОМ БЛОКЕ
Low 0x7A: внутренний RC 9,6 МГц, CKDIV8 отключён (бит 4 равен 1),
делитель /1. High 0xFF — заводской High Fuse; как указано в документах
архива, менять его для этих прошивок не требуется.
Сверено с Microchip ATtiny13A Data Sheet DS40002307A, §17.2,
таблицы 17-3 и 17-4 (стр. 110):
https://ww1.microchip.com/downloads/en/DeviceDoc/ATtiny13A-Data-Sheet-DS40002307A.pdf

ПРОШИВКИ
firmware.json генерируется из сохранённых файлов ATtiny13A/Music/.
Flash и EEPROM включены в каталог. Проверяются SHA-256 всех оставшихся
HEX, BIN и встроенных HTML-образов; неизвестные копии вызывают ошибку.
Актуальные варианты: ATtiny13A/Music/variants/{rhythmic,alicia,turkish-march,children,greensleeves}/.
Параметр ?firmware=<id> выбирает вариант. Папка содержит исходники, score.json,
synth.hex, eeprom.hex, build-report.json, автономный player.html; WAV может
быть справочным фрагментом. Плеер всегда исполняет AVR ROM.
Все пять вариантов имеют два резервных канала, помимо основных
партий. Сохраняются частота, фаза и огибающая; занятые слоты вытесняются по
тихому резервному каналу. Все основные и резервные каналы завершаются перед повтором.
MIDI-бинарники в проект не помещаются. События, партии, инструменты,
метаданные и оригинальные SHA-256 сохраняются в reference/*/*events.json.

Измерения спектров FluidR3 вынесены в ATtiny13A/Music/reference/fluidr3/.
Исходные документы импорта и C-прототип 2016 года сохранены отдельно.

Восстановить каталог (Python 3, только стандартная библиотека):
  python web-player/scripts/build_catalog.py
Проверить полноту и актуальность, не меняя файл:
  python web-player/scripts/build_catalog.py --check
Скрипт останавливается, если находит неизвестный образ или повреждённый HEX.

БАНК ИНСТРУМЕНТОВ ПРИ СБОРКЕ
Общий ATtiny13A/Music/instruments/bank.json хранит измеренные компактные
профили FluidR3, их GM-программы, модель огибающей, уровень и происхождение.
Доступны рояль, нейлоновая гитара, безладовый бас, скрипка, виолончель,
кларнет, флейта, отдельный мягкий рояль и off. natural-kit выбирает отдельный генератор ударных.
Назначения фиксируются в score.json и сборщике аранжировки: плеер
воспроизводит уже собранные Flash/EEPROM. Для смены тембра пересобирают
назначение, огибающую/уровень и оба HEX-файла.

tools/instrument-bank.py предоставляет load_bank(), build_eeprom(),
describe_assignments() и verify_sources(). lead/keys/pluck — имена
тональных слотов, не обязательные скрипка/клавиши/гитара. Например:
  {"lead":"flute","keys":{"instrument":"violin","level":12},
   "pluck":{"instrument":"cello","level":10},"percussion":"off"}
Уровни 0..15 применяются кодом огибающей; build_eeprom повторно их не масштабирует.

В EEPROM попадают только выбранные формы: по два регистра по 8 байт
на тональный слот, всего 48 Б; последние 16 Б содержат две формы атаки
рояля или тишину при его отсутствии. При проигрывании
EEPROM только читается. Партитура и программа находятся во Flash.
16 отсчётов по 4 бита не передают полные SF2-сэмплы, все спектральные
изменения и шумы инструментов. Минимальные ядра также используют сокращённые
модели огибающих, описанные для каждой адаптации. Подробности и добавление
измеренного тембра: ATtiny13A/Music/instruments/README.txt.

УСТРОЙСТВО
lib/engines.js загружает выбранный исполнитель. JS использует
lib/avr-reference.js и lib/renderer-js.js. WASM использует native/avr.c,
собранный в wasm/avr.wasm. Оба исполняют одинаковое подмножество инструкций
ATtiny13A при 9,6 МГц. lib/avr-core.js экспортирует тонкую JS-обёртку
lib/avr-wasm.js. C-ядро
обрабатывает счётчик/overflow Timer0, прерывания, чтение EEPROM и записи
OCR0B. Флаги SREG, стек SRAM/SPL и такты сверены с документацией Microchip;
архивный AVRCore используется для проверки музыкальной совместимости.
Оптимизированный JS-исполнитель также используется для дифференциальных
тестов C-ядра и замеров скорости.
Подробный аудит: reports/attiny13a-audit.txt. Полная таблица кодировок,
тактов и покрытия: reports/attiny13a-instructions.json. Поддерживаются
105 из 123 строк summary с учётом псевдонимов и форм адресации; 18 форм
завершаются явной ошибкой. Полная эмуляция микроконтроллера не заявляется.
Включённый образ не заменяется WAV или отдельным музыкальным синтезатором.

worker.js создаёт выбранный движок и выдаёт готовые блоки PCM. В режиме WASM
он вызывает C-ядро один раз на блок. Внутри WASM выполняются
AVR-команды, Timer0/IRQ, ресэмплинг, оба звуковых фильтра и громкость.
Один экземпляр ядра занимает фиксированные 64 КиБ памяти, host-imports нет.
В режиме JS те же операции выполняются в Worker на JavaScript, без загрузки
WASM. Звуковые фильтры и плавное изменение громкости есть в обоих движках.
AudioWorklet забирает готовые блоки
по запросу через MessageChannel; очередь фиксированная, без бесконечного
накопления. Начальный запас — 8192 отсчёта, блок — 4096 (при 48 кГц:
171 мс и 85 мс). Пауза сохраняет очередь; смена прошивки очищает её.
Опоздавшие пакеты предыдущей версии отбрасываются.

Как в исходных HTML, поток записей OCR0B линейно интерполируется
с номинальных 37,5 кГц до частоты AudioContext.
Далее внутри C: high-pass 35 Гц, low-pass и громкость. В Web Audio
выход AudioWorklet подключён напрямую к устройству; повторной фильтрации нет.
Фильтры без резонансного подъёма (Q=0,5); LP по умолчанию9 кГц.
Состояния biquad хранятся с двойной точностью между блоками. Срез и громкость
плавно меняются с постоянной времени 15 мс, начиная со следующего вычисляемого
блока. Уже готовая очередь сохраняется, поэтому отклик включает её задержку.
Осциллограмма и средний PWM берутся до фильтров и громкости.
Перерисовка осциллограммы ограничена 30 кадрами/с.
Мягкость тембров также заложена в таблицах волн EEPROM.
Двухбуферная фиксация OCR и реальные фронты PB1 не синтезируются.
Для произвольной прошивки число записей OCR0B может отличаться от числа
периодов PWM; равномерный ресэмплинг не моделирует такую разницу. Низкая частота
среза и АЧХ реального RC-фильтра могут давать другой результат на плате.

ОПТИМИЗАЦИЯ
- Инструкции и операнды декодируются один раз в типизированные массивы.
- В основном цикле — числовой switch, без повторного разбора битовых масок.
- Стек размещён в 64-байтной SRAM и управляется SPL. OCR0B передаётся скаляром.
- Пустой RJMP к самому себе пропускается до точной границы инструкции
  у следующего переполнения Timer0. ISR и отключённые IRQ не пропускаются.
- Ожидание места в MCU-очереди MOV/SUB/ANDI/CPI/BRCC пропускается только
  полными проходами; последний проход перед IRQ исполняется по инструкциям.
  Состояние каждого PWM-отсчёта сравнивается с пошаговым исполнением.
- fastBlocks исполняет серии ALU-команд, переходов и доступов к SRAM/Flash,
  сохраняя PC/SREG локально и обновляя Timer0 один раз за серию до 64 тактов.
  Серия заканчивается до overflow и перед обращением к I/O или стеку.
  Команду на границе события выполняет step(): TCNT0, TOV, число IRQ,
  задержка входа и потери совпадают с обычным исполнением.
- Пошаговый и блочный C-исполнители используют общие формулы ALU/SREG.
- step() по-прежнему выполняет ровно одну инструкцию для отладки.
  {fastIdle:false} по умолчанию отключает и fastBlocks. Режимы можно
  переключать отдельно; переопределённый step отключает fastBlocks, чтобы
  существующие хуки аудита продолжали получать свои пошаговые наблюдения.

Замер C/WASM: reports/wasm-benchmark.json, Node 22.22.3, Windows x64,
Ryzen 5 5600X. Сравниваются полные цепочки CPU, ресэмплинга, HPF/LPF
и громкости: медиана семи прогретых чередующихся запусков по три секунды.
C/WASM быстрее предыдущего JS в 1,58–1,60 раза; запас 34–46× реального времени.
Измерение не включает загрузку/компиляцию и создание ядра.
Условия, версии и SHA-256 исходников/ROM/WASM сохранены в JSON.
Повторить: node web-player/scripts/benchmark-wasm.mjs

Исторический замер JS reports/avr-benchmark.json: Node 22.22.3, Windows x64,
Ryzen 5 5600X. Медиана семи чередующихся прогретых запусков по три номинальные
секунды потока OCR0B, результат приведён к одной секунде, без времени создания ядра. Ускорение относительно архива:
Точные значения для каждой версии и хеши образов записаны в JSON.
Это измерение этого компьютера, а не обещание такой же скорости
на телефоне или в другом браузере.
Сравнение fastBlocks с предыдущим ядром, уже имеющим fastIdle:
reports/block-benchmark.json. Повторить из корня репозитория:
  node web-player/scripts/benchmark.mjs --baseline-ref 8a3ba15 --report web-player/reports/block-benchmark.json

ПРОВЕРКИ
Наборы, кандидаты оптимизаций и длительные прогоны описаны в TESTING_RU.txt.
  node --test web-player/tests/*.test.mjs
  node web-player/scripts/benchmark-wasm.mjs
  node web-player/scripts/benchmark.mjs
Все прежние проверки через lib/avr-core.js теперь исполняют C/WASM.
avr-wasm.test.mjs дополнительно сравнивает C и предыдущий JS: 65536 кодовых
слов, 48 воспроизводимых смешанных программ, счётчики около 2^31/2^32
и каждый PWM-отсчёт первых трёх секунд всех пяти прошивок, включая память/IRQ.
Проверяются сырые/фильтрованные PCM, независимые формулы biquad, смена
управления и произвольные границы блоков. SHA-256 связывают WASM с C и сборщиком.
После запуска сервера откройте /web-player/tests/browser-smoke.html:
проверяются ранний init Worker, MessageChannel и синхронность CPU/IRQ,
а C-фильтры сравниваются с прежней цепочкой Web Audio при 44,1/48/96 кГц.
Отчёт о выполненном переносе: reports/wasm-verification.json.
Тесты сравнивают текущие образы с исходными ядрами за 14 секунд значений
OCR0B. Допускается документированная разница до двух тактов из-за исправления
RETI. По тактам и всей памяти fastIdle сравнивается с пошаговым исполнением
исправленного ядра. Архив не считается эталоном флагов или стека.
avr-blocks.test.mjs сравнивает все четыре сочетания fastIdle/fastBlocks,
перебирает все байтовые операнды ALU, все значения SREG для сдвигов и унарных
команд, границы overflow, EEPROM-stall, вложенные IRQ и обновление decode.
Полный план дальнейшего тестирования всего ядра — в IMPROVEMENT_PLAN_RU.txt.
Независимые проверки сверяют арифметику, флаги, стек, все строки summary,
все 65536 кодовых слов, переходы, пропуски, IRQ, Timer0 и EEPROM.
Отдельно проверяются
встроенные ядра каждого исходного HTML, HEX, ресэмплинг на четырёх частотах,
границы аудиоблоков, ограниченная очередь, пауза и сброс AudioWorklet.
Каждый образ также рассчитывается на 60 секунд: число тактов должно
соответствовать 9,6 МГц с погрешностью границы последнего ISR (<0,43 мс).
В браузере время отсчётов сверяется с performance.now(); небольшая разница
от доставки сообщений не означает изменение темпа. Накопленное отставание
считается отдельно по реальным запросам AudioWorklet, независимо от UI.
Это проверка темпа. Фиксированная задержка звукового устройства и браузера
при старте не входит в измерение накапливающегося отставания.
Основной цикл готовит опорные точки18,75 кГц и средние для PWM 37,5 кГц.
16-байтовая очередь поглощает длинные серии музыкальных команд. ISR 15 тактов
сохраняет флаги; независимый oracle проверяет A,floor((A+B)/2),B, включая
прерывание сразу после публикации. Четыре основных и два резервных состояния занимают30 Б,
а варианты с тремя тональными партиями —25 Б,
максимальный измеренный стек 8 Б. Полные отчёты *-release-verification.json
проверяют отсутствие переполнений/опустошений очереди, потерянных IRQ,
границы нот, огибающие, копирование резервных каналов и тишину перед повтором.
Это проверка номинального AVR-кода; на плате нужны фьюзы7A/FF и проверка RC.

МУЗЫКАЛЬНАЯ СЕТКА
Ранее длительности нот округлялись отдельно, а ударные имели собственный
счётчик. Теперь единая 16-битная дробная фаза задаёт сетку шестнадцатых;
длительности хранятся в её шагах. Явные лиги кодируются HOLD, повторные
ноты получают новую атаку с сохранением DDS-фазы. Скрипка 01 достигает
полной громкости примерно за 54,6 мс, а не 273 мс. Фортепиано 02/03
атакуется сразу и затухает; духовой/струнные 04 атакуются мягко и удерживаются.
Greensleeves сохраняет 6/8 и затакт, а не переводится в 4/4.

Упаковщик tools/pack-score.py автоматически находит повторные команды,
подбирает разбиение динамическим программированием и использует общие
суффиксы. Считается полная цена фраз, завершений и плейлиста.
Поиск выбирает самый компактный найденный вариант, без гарантии
глобального математического минимума. Распаковка сохраняет все команды
после документированной MIDI-редукции, включая начало и повторные Note On.
SHA-256 распакованного потока сверяется с реально выполненными AVR-командами.

  python tools/build-rhythmic.py
  python tools/arrange-turkish-march.py
  python tools/arrange-children.py
  python tools/arrange-greensleeves.py
  python tools/test-instrument-bank.py
  python tools/test-score-format.py
  python tools/test-pack-score.py
  python tools/test-midi-reader.py
  python tools/assemble-avr.py --verify
  node tools/audit-rhythm.mjs rhythmic
  node tools/audit-rhythm.mjs turkish-march
  node tools/audit-rhythm.mjs children
  node tools/audit-rhythm.mjs greensleeves

Сборщики адаптаций выбирают инструменты и специализируют ядро под свои
партии. Общий build-rhythmic.py пересобирает сохранённую score.json,
включая размер 6/8. engine: "instrument-bank" включает выбор огибающих
по назначениям instruments и удаление выключенных генераторов. Обычная сборка использует
сохранённый банк: SF2, аудиодвижок и NumPy для неё не нужны.

Актуальные полные проверки пяти образов: reports/<id>-release-verification.json.
Их SHA-256 относятся к конкретному ROM и EEPROM. Максимальная ошибка
музыкальных границ Люмьера около 21,2 мс за222с; базовый тик13,653 мс.
Старые отчёты относятся к историческим ROM. Исходная причина сбоя ритма:
reports/score-timing-audit.txt. Производительность: reports/avr-benchmark.json.
План: IMPROVEMENT_PLAN_RU.txt.

СБОРКА C/WASM
Локальная установка инструментов Windows: ../tools/setup.ps1;
инструкция ../tools/SETUP_RU.txt. После неё dot-source build/toolchains/env.ps1.
Нужен Clang и готовый Emscripten sysroot. Сборщик вызывает clang напрямую,
не меняет SDK и не требует emcc, npm-пакетов или глобальной установки:
  node web-player/scripts/build-wasm.mjs --emsdk C:/path/to/emsdk
При заданной переменной EMSDK параметр можно опустить.
Повторная сборка обновляет wasm/avr.wasm и wasm/build.json с версиями,
флагами и хешами. После изменения C обязательно пересобрать WASM и запустить
тесты. Подробности ABI и лицензии библиотек — native/README.txt.

ПРЕОБРАЗОВАНИЕ ВНЕШНЕГО MIDI
  python tools/midi-events.py "C:/external/song.mid" build/song-events.json
  python tools/midi-to-firmware.py build/song-events.json --output build/song --lead-track 1
Подробная инструкция и ограничения: ../tools/MIDI_TO_FIRMWARE_RU.txt.
JSON содержит все события источника; музыкальная редукция выполняется отдельно.

Проверка частотной сетки:
  node tools/audit-frequency-grid.mjs
Все записи ROM сверяются с A4=440Гц; каждый DDS-шаг исполняется на AVR
в каждом состоянии на пяти границах фазы/переноса. Итоги и частоты каждой
ноты: reports/frequency-grid-verification.json. Басовые PitchBend Children
сохранены в исходном JSON, но в компактную нотную адаптацию не входят.

РЕЧЬ MINILPC HQ4
Публичный сайт: https://witali.github.io/MicroMusic/web-player/?collection=hq4
Он работает без внешнего архива: hq4-firmware.json содержит три варианта HQ4-T и четыре
исторических образа HQ4, как firmware.json для музыкальных прошивок.
Автоподбор: ?collection=hq4&firmware=hq4-chego-auto (STOI ≥0,9005).
Более свободный режим: ?collection=hq4&firmware=hq4-chego-spectrum (STOI ≥0,89).
Предыдущий HQ4-T: ?collection=hq4&firmware=hq4-chego-timbre.
HQ4-T добавляет восстановление тембра в AVR: 979 Б Flash, 7,5 кГц.
Для сравнения с исходным HQ4 включено выравнивание громкости, которое
можно отключить. Полный отчёт: ../ATtiny13A/Sound/codec/timbre/README.md.
Для пересборки HQ4-T нужны также codec/requirements.txt (numpy/numba/scipy/pystoi).
Автоматический кодировщик, контрольные точки и метрики: ../ATtiny13A/Sound/codec/AUTO_ENCODER.md.
Пересборка каталога из сохранённого ассемблера:
  python tools/build-hq4-catalog.py --avr-bin build/toolchains/avr-7.3.0/bin
Добавьте --check для проверки, что опубликованный каталог не устарел.

Для трёх речевых примеров и maximum-STOI варианта используется тот же
плеер, Worker/AudioWorklet и общие JS/WASM-ядра. Из корня репозитория:
  python tools/prepare-hq4-preview.py --archive "<Downloads>/MicroMusic_COMPLETE_RESEARCH_HANDOFF_2026-10-22(2).zip"
  node web-player/scripts/serve.mjs 8145
Открыть http://127.0.0.1:8145/web-player/?collection=hq4
Сценарий проверяет хеши и восстанавливает медиа в игнорируемый
build/hq4-preview. Доступны оригинальные WAV и плеер из ChatGPT.
Указатель эталонов: ../ATtiny13A/Sound/AUDIO_REFERENCES.md.
Официальный аудит и сравнение: reports/hq4-audit-2026-10-22.md.
